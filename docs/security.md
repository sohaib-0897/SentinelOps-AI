# Security model and targeted review

Production configuration requires a durable database, disabled demo controls, a server-only operator token of at least thirty-two characters, explicit CORS origins, and a separate GCP executor identity when cloud remediation is enabled. All `/api/` reads, mutations and SSE require the configured token. Cloud Run IAM additionally protects API and dashboard invocation. The dashboard is private by default and its proxy keeps operator/metadata identity tokens on the server.

Actual request bytes are limited to one megabyte at both API and proxy, including requests without Content-Length. Telemetry is bounded and scoped to `orders-api`, rejects timestamps more than five minutes ahead, deduplicates replay, and refuses to mutate an active local scenario. The proxy validates path segments/query bounds and rejects browser cross-origin mutation. Runtime endpoint configuration is trusted administrator configuration, not a user-controlled fetch target.

Privileged actions follow structured plan → risk policy → exact approval → atomic execution claim → allow-listed executor → audit. No agent receives IAM credentials, arbitrary commands or generic HTTP execution tools. The cloud executor uses a short-lived impersonated access token and updates only a traffic mask after validating service, revision, readiness, serving precondition and etag. IAM limits service mutation to `orders-api`; GCP IAM has no field-level traffic-only role, so application validation remains necessary. A compromised API can assume its scoped executor; these are separate credentials and grants, not an isolated hardware trust boundary.

Runtime identities are separate for API, dashboard, telemetry, analytics, scheduler and executor. API reads need project-wide Logging/Monitoring/Run viewer roles, and Vertex/job-user access; source resource filters constrain queries in code. Analytics gets table-scoped writes and its subscription. The API cannot mutate its own Run service or other workloads. The demonstration target has no project role grants. ADC, service identities and optional GitHub WIF replace downloadable JSON keys.

Secret placeholders have no Terraform secret versions or values. Bootstrap generates a cryptographic token into Secret Manager through stdin after explicit authorization, never arguments/state/Git. Cloud SQL uses IAM connector authentication, no authorized public networks and encrypted transport. SQL grants permit only the incident database/schema; migrations run as its application owner. Docker runs the API as UID 10001 and dashboard as node, with read-only Compose filesystems and no-new-privileges.

The final review covers tracked credentials/env/state, subprocess/shell paths, runbook traversal, byte limits, authentication/SSE, proxy SSRF/origin handling, approval replay/tampering, secret redaction, IAM, CORS and container users. Identified issues were fixed in separate commits with regressions: chunked body limits, future-clock/scenario isolation, proxy path/body bounds, executor credentials, wildcard CORS and paused ordered publication. Fixed subprocess commands use resolved executables/argument arrays, not user-generated shell code. Pattern redaction complements source-side hygiene; it is not a guarantee that every possible secret can be recognized.

Live IAM enforcement, authenticated Cloud Run identity exchange, database grants and cloud model behavior still require integration checks. Store Terraform state in a private versioned backend before shared production operation; local state and plans are ignored, sensitive operational files. No production security claim is inferred from mocks alone.
